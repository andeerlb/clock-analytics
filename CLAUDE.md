# CLAUDE.md

## Migrations (SQLite / tauri-plugin-sql)

- **Never edit an already-applied migration file.** Real users' `_sqlx_migrations.checksum` is pinned to its exact byte content — even a whitespace change breaks every machine that already ran it (`MigrateError::VersionMismatch`, blocks app startup entirely). Add a new migration instead. A migration that failed and rolled back (check `_sqlx_migrations` on a real copy of the db — a failed migration leaves zero trace there) is the only case where editing in place is safe.
- **Every migration runs inside a transaction**, no exceptions — `tauri-plugin-sql`'s `MigrationList::resolve()` hardcodes `no_tx: false`. `PRAGMA foreign_keys = OFF` is a documented no-op mid-transaction, so it does **not** suppress FK enforcement during a migration — `DROP TABLE` still performs its implicit FK-checked delete. A migration that needs to rebuild a table with incoming FK references must rebuild the whole dependency chain under `_new`-suffixed names (each referencing the others' `_new` name), copy data, drop every old table child-first, then rename every `_new` table into place parent-first — see `src-tauri/migrations/0067_employee_unique_per_client.sql` for a worked example and its header comment for the two approaches that look like they'd work but don't (`PRAGMA foreign_keys=OFF`, `PRAGMA legacy_alter_table=ON`).
- **Never ship runtime "self-healing" migration-repair logic.** It was tried once (a `.setup()` hook that detected "schema already fixed but bookkeeping stale" and deleted the stale `_sqlx_migrations` row so the real migrator would retry) and it caused exactly the bug it was meant to prevent: on a database a human had *manually* fixed, the hook kept re-deleting the correct bookkeeping row on every single launch, since it can't tell "stale from an old broken build" apart from "already correct" — it just checks whether the schema looks fixed. It also cannot know it's already served its one purpose and should stop running. If a migration shipped broken, fix it with a new migration (or, for something too dangerous to trust in a fully-automated release before it's been proven on your own machine, a one-time support tool that runs once and is deleted from the codebase after) — never code that keeps deciding on its own, forever, whether to intervene.
- **Before shipping a migration that touches an existing table's structure, test it against a copy of real data with actual cross-table FK references in place** — not an empty database, and not just a manual `sqlite3` CLI session (that doesn't reproduce the always-on-transaction behavior above). An empty database won't surface an FK violation; that only appears once there are real child rows for a rebuilt parent table to conflict with, which is exactly how migration 67 shipped broken the first time.
